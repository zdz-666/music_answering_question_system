# 检索链路重构：由大模型托管检索决策

## Context（为什么做）

当前信息检索链路有两个问题：

1. **检索通道由前端勾选框硬控**。`use_web_search` / `use_knowledge_base` 两个布尔从 [App.js](file:///d:/bishe/music-chatbot-frontend/src/App.js#L286-L311) 一路透传到 [rag.py](file:///d:/bishe/rag.py#L319-L327)，用户勾了就一定跑、没勾就一定不跑，系统自己不会判断这次提问到底需不需要检索、该走哪条路。
2. **网络检索只取一条**。[web_search](file:///d:/bishe/rag.py#L156-L176) 里 `result = response.get("results")[0]` 只留最相关的一条，Tavily 请求本来就带了 `max_results=5`，剩下 4 条被直接丢掉；而且命中空列表时会抛 `IndexError`。
3. **没有"检索够不够"的判断**。一轮检索完就直接进自反思和生成，信息不足时不会换个语句再查一次。

目标：让链路自己判断「要不要检索、检索哪条通道」和「检索到的信息够不够、要不要换个语句再查」，并把网络结果从 1 条放宽到 5 条。

## 已确认的决策（与用户对齐）

| 决策点 | 结论 |
| --- | --- |
| 前端开关与新决策的关系 | **大模型完全接管**。前端两个勾选框直接删掉，`QueryRequest` 与 `/api/upload` 的对应字段一并移除，不留兼容层 |
| 补充检索的通道 | **沿用首轮通道**，不每轮重新决策 |
| 补充检索轮数 | **最多 2 轮**（首轮之外），硬上限 |
| 多轮结果合并 | **追加去重后交给现有的 `self_reflection`**，不新增汇总用的 LLM 步骤 |

## 方案总览：重构后的链路

```
提问
 │
 ├─ retrieval_planner        ← 新增：LLM 决定走知识库 / 网络 / 两者 / 都不走
 │
 ├─ (通道含知识库) collection_router → query_rewriting → vector_search → rerank
 ├─ (通道含网络)   web_rewriting → web_search（取 5 条）
 │
 ├─ 补充检索循环（≤ MAX_SUPPLEMENT_ROUNDS 轮）
 │    retrieval_sufficiency   ← 新增：LLM 判断信息够不够，不够则给出新检索语句
 │         └─ 用新语句在首轮通道里再查一遍（复用首轮集合名）→ 追加去重
 │
 ├─ self_reflection          ← 复用现有步骤，过滤多轮合并后的结果
 │
 └─ generate
```

新增两个 LLM 决策步骤，均沿用 [collection_router.py](file:///d:/bishe/collection_router.py) 已确立的 `llm.with_structured_output(Pydantic)` 范式。

## 详细改动

### 1. 新建 `d:\bishe\retrieval_planner.py`

承载两个结构化决策，风格对齐 [collection_router.py](file:///d:/bishe/collection_router.py)（模块级函数 + Pydantic 模型 + `get_chat_model()`）。

```python
class SearchPlan(BaseModel):
    # 刻意给 default=True：模型漏字段时按"开启"处理（fail-open），
    # 只会多检索一次，不会静默把通道关掉
    use_knowledge_base: bool = Field(default=True, description="…")
    use_web_search: bool = Field(default=True, description="…")

def plan_retrieval_channels(question: str) -> SearchPlan:
    """返回本次提问要走哪些检索通道。异常时兜底为两者都开（与旧默认一致）。"""

class RetrievalAssessment(BaseModel):
    is_sufficient: bool = Field(default=False, description="已检索信息是否足以回答")
    new_query: str = Field(default="", description="不够时给出的新检索语句，够时留空")

def judge_retrieval_sufficiency(question, kb_text, web_text, channel, round_index) -> RetrievalAssessment:
    """判断检索是否充分，不够时给出新的检索语句。"""
```

要点：
- 用**两个 bool** 而不是单字段枚举，贴合用户「是否启用知识库、是否启用网络、还是都启用」的表述；`default=True` 消除「字段缺省 → False → 通道被误关」的陷阱。
- `plan_retrieval_channels` 调用包在 `log_step("retrieval_planner", input=question)` 里，`span.output` 记 `{use_knowledge_base, use_web_search}`。
- `judge_retrieval_sufficiency` 包在 `log_step("retrieval_sufficiency", input={question, channel}, round_index=n)` 里，`span.output` 记判断结果与新语句。
- 内部 `try/except` 兜底：规划模型挂掉 → 返回两者都开；审查模型挂掉 → 由调用方 `break`（见下）。

**e. 新增补充检索循环**

```python
def _supplement_retrieval(question, channel, collection_list, kb_chunks, web_items):
    seen = {_normalize_query(question)}
    for round_index in range(1, MAX_SUPPLEMENT_ROUNDS + 1):   # 用 for，结构上不可能超限
        assessment = judge_retrieval_sufficiency(...)          # try/except → break
        if assessment.is_sufficient:
            break
        new_query = assessment.new_query.strip()
        if not new_query or _normalize_query(new_query) in seen:
            break                                              # 无有效进展就收手
        seen.add(_normalize_query(new_query))
        try:
            if channel 含知识库: kb_chunks = merge_kb_chunks(kb_chunks, get_vector_search(new_query, collection_list))
            if channel 含网络:   web_items = merge_web_items(web_items, get_web_search(new_query))
        except Exception:
            break                                              # 补充轮失败不打死整条问答
    return kb_chunks, web_items
```

**f. 抽出 `_retrieve_and_reflect(question) -> str`，消除 `get_result` / `get_result_evaluate` 的重复**

两个公开函数当前几乎逐行重复，抽出检索半段后各自只保留真正不同的生成 prompt：

```python
def _retrieve_and_reflect(question: str) -> str:
    plan = plan_retrieval_channels(question)        # ← 必须最先，早于 router / web_rewriting
    kb_chunks, web_items, collection_list = [], [], []
    if plan.use_knowledge_base:
        collection_list = route_collections(question)
        kb_chunks = get_vector_search(question, collection_list)
    if plan.use_web_search:
        web_items = get_web_search(question)
    if plan.use_knowledge_base or plan.use_web_search:
        kb_chunks, web_items = _supplement_retrieval(...)
        context = self_reflection(question, format_kb_chunks(kb_chunks), format_web_items(web_items))
    else:
        context = "本次提问无需检索，请基于你自身的音乐知识作答。"
    return context
```

- `get_result(query, history_string)` → `_retrieve_and_reflect` + 原有乐典 prompt + `generate`；**仍然返回 `AIMessage`**（[main.py](file:///d:/bishe/main.py#L80-L81) 取 `.content`），契约不变。
- `get_result_evaluate(query)` → 去掉两个布尔形参，改走同一条检索链路，返回 `(context, answer)`。
- 生成半段抽成 `_generate(prompt_template, variables, **step_fields)` 复用（两端仅 prompt 与变量不同）。
- 通道为 `none` 时跳过 `self_reflection`（没有待过滤的内容，省一次 LLM 调用）。

## 明确不做的事

- 不加「二次检索结果由 LLM 汇总」的额外步骤——按决策走追加去重 + 现有 `self_reflection`。
- 不做近似的语义去重（embedding 相似度），只用精确键去重。
- 不加 context 总量上限（`MAX_CONTEXT_CHUNKS`）——轮数已被 2 封顶，先不做；若实测 prompt 过大再加。
- 不调整「路由先于改写」这个既有顺序（上一轮已作为观察项单独提出）。
- 不删 `self_reflection.result` 那条重复日志（同样是待用户决定的既有观察项）。

## 验证方案

用构造日志 + 真实链路两条路验证，重点断言「某步骤**完全没出现**」而不是只看答案对不对：

1. **通道真的被关掉**：发寒暄类问题，日志里 `retrieval_planner` 的 `step.done` 应显示两条通道都为 false，且全链路**不应出现** `collection_router` / `web_rewriting` / `web_search` / `vector_search` 任何一个 span。
2. **单通道**：问「我最喜欢的歌手」→ 应只有知识库链路；问时事类问题 → 应只有网络链路（无 `collection_router` / `vector_search`）。
3. **补充检索真的发生**：用 `python trace_view.py <日志> --request-id <id>` 看树，`retrieval_sufficiency` 出现次数 = 补充轮数；不充分时其后应出现新一组 `vector_search` / `web_search`。也可直接数 `"step":"web_search"` 的出现次数。
4. **五条结果进了 prompt**：`web_search` 的 `step.done` 里 `output` 数组应有 5 个元素；`self_reflection` 的 `input.web_result` 里应能看到 `[1]`…`[5]` 五个 `URL：`。
5. **去重与轮数上限**：构造审查模型持续返回「不充分」，确认总轮数不超过 2；确认重复语句会被 `break` 拦下。
6. **降级**：把 `TAVILY_API_KEY` 改成无效值跑一遍，补充轮失败应只留 `supplement` 相关 warning 并正常出答案。
7. **回归**：跑 `python llm_ev.py`（新签名）确认不报 TypeError；`/api/chat`、`/api/upload`、三个 knowledge 端点各打一次。
8. **前端**：`npm start` 后用 browser 子代理确认聊天页不再出现两个勾选框与「当前设置」提示，且发送消息仍正常返回。

## 风险最高的三个点与规避

1. **通道决策放错位置 → 关掉的通道仍被白跑**。规避：`plan_retrieval_channels` 必须是 `_retrieve_and_reflect` 第一行，早于 `collection_router` / `web_rewriting`；用 `if plan.use_web_search:` 分支而不是先跑再丢弃。
2. **`web_search`（dict→list[dict]）与 `get_vector_search`（str→list[str]）契约变更漏改下游 → prompt 里出现 Python 字面量**。规避：面向 prompt 的文本统一只经 `format_kb_chunks` / `format_web_items` 出口；`_retrieve_and_reflect` 返回类型固定 `str`；`self_reflection` 签名不变；改完 grep 一遍 `web_result` / `vector_result` / `context` 的赋值点。
3. **补充检索失控（无限循环 / 无效重试 / 异常打成 500）**。规避：`for` 循环 + `MAX_SUPPLEMENT_ROUNDS` 硬上限；`seen` 语句去重，无有效新语句即 `break`；审查与补充检索各自 `try/except → break`，绝不向上抛。

另有一个易错点：知识库 chunk 与网络 `content` 常含 `{}`（上传的 XML、歌词）。所有结果必须作为**变量值**传给 `ChatPromptTemplate`（现状已如此），格式化函数绝不能把内容拼进模板字符串本身。

## 成本与延迟影响（最坏情况）

- 基线约 5 次 LLM 调用；新增 `retrieval_planner` 固定 +1。
- `both` 通道下每轮补充检索 +3 次（`retrieval_sufficiency` + `query_rewriting` + `web_rewriting`），2 轮共 +6。
- **最坏约 12 次 LLM 调用**，Tavily 最多 3 次；按单次 1.5-2s 估，最坏延迟从约 8s 升到 20-25s。
- 典型情况只多 1 次（`retrieval_planner`）；通道为「都不检索」时反而少 1 次（跳过 `self_reflection`）。上限由 `MAX_SUPPLEMENT_ROUNDS` 硬控，可调。
